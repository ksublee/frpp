# FRPP 분리 시제품 검토

2026-10-17. 기준은 `emhawkes` 커밋 `ff88915`(1.0.0), 같은 컴퓨터의 Windows/R 4.5.1이다.
패키지는 emhawkes 옆의 frpp 폴더와 별도 Git 저장소로 분리했다. [패키지 사용법](../README.md)을 참고한다. 배포 이름과 API는 아직 가칭이다.
본체의 R·C++ 코드, NAMESPACE, DESCRIPTION 및 CRAN 제출 파일은 수정하지 않았다.
기존 사용자 수정·스테이징 상태와 빌드 파일도 보존했다. 이 문서는 초기 실험 결과이며, 이후 폴더와 저장소를 분리했다.

## 판단

**단방향 의존과 합성 객체는 이전의 출발점으로 적절하다.** 기존 기능을 유지하면서
모형을 분리해 보관할 수 있고, FRPP 우도 조합을 별도 패키지에서 계산할 수도 있었다.
세 번째 공통 엔진 패키지를 만들 필요는 이번 실험에서 드러나지 않았다.

다만 현재 공개 API만으로 완전한 분리를 마치기는 어렵다. 다음 단계는
`emhawkes`가 구간별 구동량 적분과 사건 전후 상태를 반환하는 작은 공개 API의 설계다.
그 뒤 시뮬레이션과 분포 함수 바인딩을 옮기고, 추정 모수의 척도 규칙을 정하는 순서가 좋다.
CRAN 제출 직후 본체에서 FRPP 슬롯과 분기를 제거하는 변경은 하지 않았다.

## 구현한 경계

| 항목 | 상태 |
| --- | --- |
| 패키지 의존 | `frpp → emhawkes`; 본체는 새 패키지를 참조하지 않음 |
| 모형 객체 | `frpp_spec(kernel, residual)`; `hspec`을 상속하지 않음 |
| 잔차분포 | 모수와 d/p/q/r 함수를 `residual_law`에 보관 |
| 기존 객체 변환 | `as_frpp()`와 `as_legacy_hspec()`; 함수와 기본 인자 바인딩 보존 |
| 시뮬레이션 | 기존 공개 `hsim()`을 통한 호환 경로 |
| 기본 우도 | 기존 공개 `logLik()`을 통한 호환 경로 |
| 숫자형 독립 우도 | 공개 Hawkes 추론의 상태를 이용하되 FRPP 밀도·생존확률은 별도 조합 |
| 새 추정 API | 아직 추가하지 않음 |

내부 함수 `emhawkes:::` 호출, 내부 namespace 접근, 별도 native 호출은 없다.
단, 호환 경로는 아직 본체의 FRPP 계산과 `set_residual()`에 의존한다.
따라서 이 시제품을 본체의 FRPP 제거가 끝난 상태로 해석하면 안 된다.

## 검증 결과

- 3개 커널(단변량·2차원·매핑을 갖는 2×4 커널), Gamma·Exp·tzexp 분포,
  seed 2개, 초기 행만/35행 조합 **36개**에서 전체 출력 자료와 최종 난수 상태가 정확히 같았다.
- 호환 우도는 기존 우도와 정확히 같았다. 독립 우도의 최대 절대 차이는
  `4.2632564145606011e-14`였다. 반환값의 이름·차원은 별도로 확인했다.
- 숫자형 마크 효과와 매핑이 있는 모형에서 전체 사건 이력을 직접 합산하고
  수치 적분한 결과와 비교했다. 구간 적분 최대 오차는 `5.5511151231257827e-17`이었다.
  R·C++ 두 상태 계산 경로를 각각 검사했다.
- 상태 의존 baseline, 현재 성분 의존 impact, 마크 생성 callback과 N0/Nc0도
  호환 경로에서 출력·난수·추론 결과를 유지했다.
- Exp(1)의 Hawkes 우도 복원, 긴 구간의 로그 생존확률, 동시 사건,
  사건이 부족한 유형의 빈 잔차, 초기 행의 난수 비소비를 확인했다.
- 저장한 새 객체와 이전 객체 변환본을 `methods`와 `emhawkes`가 연결되지 않은
  새 세션에서 복원했다. `frpp`만 연결한 상태에서 생성과 우도가 작동했다.
- 시제품의 `R CMD check`는 예제·테스트 3개 파일·PDF 매뉴얼을 포함하여 `Status: OK`였다.
  다른 운영체제의 검사는 이번 로컬 시제품 범위에 포함하지 않았다.

## 모형 규칙과 식별성

후보 잔차를 **모든 차원에 대해 매 글로벌 사건마다** 다시 생성하는 동작을 유지했다.
기본 강도만 있는 2차원 Gamma 예에서 차원별 renewal 시계를 유지하는 대안은
기존 모형과 로그우도가 약 `1.872362` 달랐다. 별도 시계 유지로 바꾸는 것은 모형 변경이다.

기본 강도만 있는 Exp 잔차 예에서 `(mu, rate)=(.2,4),(.4,2),(.8,1)`은 같은 우도를 냈다.
자유로운 두 척도를 함께 추정하는 API를 추가하기 전에 잔차 척도 정규화나
고정 모수 규칙이 필요하다. 임의 분포의 평균을 추측하지 않았으며,
`auto` 초기화는 기존 FRPP처럼 zero로 유지했다.

## 작은 성능 실험

2차원·4커널, Gamma(2,2), 숫자형 모형에서 전체 우도 호출을 비교했다.
설치·컴파일은 제외했고, 준비 실행 후 순서를 번갈아 3회 실행한 중앙값이다.
측정 중 다른 무거운 작업은 실행하지 않았다.

| 출력 행 수 | 계산 경로 | 중앙값(초) | 누적 메모리 할당(바이트) |
| ---: | --- | ---: | ---: |
| 100 | 기존 FRPP | 0.00 | 41,920 |
| 100 | 새 객체의 호환 경로 | 0.00 | 41,920 |
| 100 | 독립 우도 | 0.01 | 50,392 |
| 2,000 | 기존 FRPP | 0.13 | 809,520 |
| 2,000 | 새 객체의 호환 경로 | 0.14 | 809,520 |
| 2,000 | 독립 우도 | 0.14 | 969,992 |

100행 시간은 타이머 분해능에 가까워 속도비를 해석하지 않는다.
2,000행 독립 우도의 절대 차이는 `1.36424205265939e-11`이었다.
메모리 값은 `Rprofmem()`의 **누적 할당량**이며 최대 점유 메모리가 아니다.
이 한 모형에서 속도 개선은 확인되지 않았다. 전체 경로를 받는 우회 방식이
독립 우도 경로의 추가 할당을 만드는 만큼, 공통 API에서 필요한 출력만 선택할 필요가 있다.

재현 스크립트: [benchmark.R](benchmark.R).
시제품과 기준 emhawkes가 설치된 라이브러리를 사용해 다음을 실행한다.

```sh
Rscript --vanilla tools/benchmark.R OUTPUT_DIRECTORY
```

## 다음 작업 후보

1. `hspec`의 잔차 슬롯을 읽지 않는 공통 경로 API의 입력·출력 계약을 정한다.
   구간 적분, 사건 전후 구동량, 초기 상태, 매핑을 명시하고 필요한 이력만 반환한다.
2. 숫자형 모형으로 독립 FRPP 시뮬레이션을 구현해 현재 후보 재생성 규칙과 난수 순서를 비교한다.
   기존 호환 경로는 비교 기준으로 남긴다.
3. 잔차 척도와 커널 척도의 식별 규칙을 정한 뒤 모수 매핑·추정 결과 복원을 옮긴다.

이 단계들이 검증된 뒤 본체의 기존 FRPP 인터페이스를 이전·축소할 수 있다.

측정 원자료: [benchmark.csv](prototype-results/benchmark.csv), [R 세션](prototype-results/session-info.txt).

## 독립 폴더 검증

`packages/frpp`에서 별도로 설치·빌드한 소스도 테스트 3개 파일과 PDF 매뉴얼을 포함해
`R CMD check`에서 `Status: OK`였다. 기능 코드는 초기 검증본과 동일하다.
시제품과 관련 문서를 모두 이전했으며 `emhawkes/tools`의 임시 사본은 백업 후 제거했다.
Git 저장소는 독립적으로 초기화했다. GitHub 원격 저장소는 아직 연결하지 않았다.
